Inspired by these two videos (1,2) by the youtube channel Deckard, I decided to create a program which could automatically generate these puzzles to be played. While using a grid would probably have provided additional features to the graph to allow for a faster puzzle generation algorithm, I wanted the framework to be flexible enough to allow for more complex graphs. The algorithm is relatively simple:

  • Generate a random set of n subgraphs which satisfy the criteria
  • Assign the smallest m subgraphs to the party the user will play as where m is the smallest number of districts needed to win
  • Randomly assign k of the nodes in that subgraph to the user party where k is the smallest number required to win, then fill the remaining with competing parties
  • In the remaining districts assign a random party such that the user party will not lose
  • Assign the nodes such that the random party wins
This game is currently only playable in a terminal with a text based UI as it is something I threw together quickly, but I plan to make a more usable web UI which can be played here.

In this project I worked with collaborators Helen Wand, Dylan Lutrell, and Ian Liu to develop a system which could evaluate and solve handwritten mathematical expressions as part of our image recognition course. As the course had covered a wide range of historical and modern approaches we used several different methods to conduct the HMRE. This problem is somewhat more complex than basic OCR, as you are generating a structured sequence of symbols which may not be clearly vertically delimited. For this project we used 3 different datasets CROHME with 80k individual characters, a Kaggle handwritten characters dataset, and a dataset of 3200 of our own handwritten digits.

For our more traditional approach, we split the process into a pipeline: separating the characters, classifying the characters, and then feeding that to a CAS system. To split the characters we simply created bounding boxes on connected components, and combined them based on vertical overlap. The decision to simplify to use vertically deliniated characters was made for the sake of development time given we only had a few weeks to complete the project. We then trained a CNN on our character datasets which had reasonable performance for the scope of our project (.87 train, .69 test). This setup allowed us to feed our expressions into latex2sympy to solve the expressions.

Our more modern approach was to use the TROCR model published to Huggingface by Microsoft. We then finetuned this model on the CROHME dataset to make it better suited for our usecase. While this approach was very effective it was also quite resource intensive and so would not be practical for something like on device computation.

As a final project for a deep learning course at Rose Hulman, I worked with a team to predict missing salary information from linkedin job postings from a Kaggle Dataset. Due to the formatings of the postings we had to do a lot of data preprocessing to make the dataset usable, such as filtering out inaccurate data, vectorizing text features, one hot and multi-hot encodings and PCA. In the end using a deep learning model with L2 regularization, masking, custom loss functions, and batch normalization we were able to get a reasonably accurate prediction of salaries given incomplete data.

Queue is a web application dedicated to helping users prioritize their tasks using computer science principles and the priority queue data structure. Users are able to input thier obligations into the website, and select a function for the priority of the project in the queue. These functions operate on the variables of the item in order to prioritize the queue on each refresh. This allows items with sooner due dates to pass those of higher priority as the due dates arrive. Power users can also choose to define their own functions in order to better fit their own needs.
